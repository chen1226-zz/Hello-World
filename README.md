# 幂等消费（exactly-once 效果）

消费端从外部上游拉取事件并落库（`ledger` 记账）。`make replay` 会把
同一批业务事件**投递两遍**（含乱序、重复 `event_id`），最终汇总必须
与「只处理一遍」完全一致。

```bash
make replay   # 复现：同一批事件投递两遍后比对汇总
make test     # 单测：重复投递 / 并发竞争 / kill -9 后重启
```

## 设计

### 幂等键

去重键 = 上游下发的**业务事件 ID**（`event_id`）。它由上游在事件
首次产生时分配，重试、重放、乱序投递时都保持不变。关键约束：幂等键
只允许包含业务标识，绝不能混入时间戳、机器名、随机数等每次投递都会
变化的量——否则同一条业务的每次投递都会生成不同的「新键」，去重表
永远 miss，等于没有去重。

### 唯一约束

```sql
CREATE TABLE processed (
    event_id     TEXT PRIMARY KEY,   -- 唯一约束是防错的最后一道防线
    processed_at TEXT NOT NULL ...
);
```

`processed.event_id` 上的 `PRIMARY KEY`（唯一约束）由数据库保证：
无论多并发、多实例，同一 `event_id` 的去重记录最多插入 1 行。插入
使用 `INSERT OR IGNORE`，`rowcount == 0` 即「已被处理」，直接跳过
业务写入。

### 事务边界

**去重记录与业务写入必须在同一事务**（`BEGIN IMMEDIATE` … `COMMIT`）：

1. `BEGIN IMMEDIATE`：立即取写锁，串行化并发消费者；
2. `INSERT OR IGNORE INTO processed`：先占去重位；
3. `INSERT INTO ledger`：业务写入；
4. `COMMIT`：两者一起生效。

崩溃只可能产生两种结果：事务未提交 → 两种写入一起回滚（下次重试
重新处理）；事务已提交 → 两种写入一起生效（下次重试被去重）。
不可能出现「去重了但没落库」或「落库了但没记去重」。

### 并发

多个消费者（线程或进程，各自持有独立连接）抢同一条事件时，
`BEGIN IMMEDIATE` 让写者串行：后到者在 `busy_timeout` 内等待，拿到
锁后其 `INSERT OR IGNORE` 被唯一约束吸收（`rowcount == 0`），于是
跳过业务写入。唯一约束是最终保证，锁只是减少冲突。

## 原实现为什么失效

本仓库初始版本埋了两个 bug，分别对应「重放必现」和「偶发重复」：

1. **幂等键含时间戳。** 原实现把「收到时间」拼进了去重键，
   例如 `f"{event_id}:{time.time()}"`。
   时间戳在每次投递时都不同，
   所以同一条业务每次都会算出一个新键。
   新键在去重表里查不到旧记录，
   于是业务被再次记账。
   这解释了「小流量时看起来正常、
   把历史消息整体重放必现重复」的现象。

2. **事务边界错误。** 原实现把「记去重」和「写业务」
   拆成了两个事务：先提交去重记录，
   再提交业务写入。
   两个事务之间存在崩溃窗口：
   若在去重提交后、业务提交前宕机，
   重启后该事件会被判为「已处理」而跳过，
   出现「去重了但没落库」；
   反过来若顺序对调，
   则可能出现「落库了但没记去重」，
   之后重试会再次记账。
   这解释了「偶发重复」：
   只有在恰好的时刻崩溃才会触发。

修复方法见上文「设计」：
幂等键只含业务 ID，
去重记录与业务写入合并为同一事务，
并用唯一约束兜底。
