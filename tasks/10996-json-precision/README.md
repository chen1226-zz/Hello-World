# 订单服务 JSON 精度修复

## 问题

1. 18–19 位订单号落库后末几位被抹成 0，同一订单出现两条记录；
2. 金额偶发差 1 分，如 `1234.56` 读回变成 `1234.5599999999`。

## 浮点为什么会丢精度

- **整数**：IEEE 754 双精度浮点的尾数只有 52 位（约 15–16 位十进制有效数字）。
  超过 2^53（9007199254740992）的整数无法被精确表示，会被舍入到最近的
  可表示值——18–19 位订单号的末几位因此被抹掉，两个不同订单号可能舍入
  到同一个浮点值，去重后看似"同一订单两条记录"。
- **小数**：`1234.56` 这类十进制小数在二进制下是无限循环小数，浮点只能
  存一个近似值；序列化时这个误差就暴露为 `1234.5599999999`，对账差 1 分。
- 小数值的测试用例（如 `1.5`、`0.5`）恰好在二进制下可精确表示，所以
  只有真实数据才暴露问题。

## 替代策略（全程零浮点）

- **解析**：`json.loads(..., parse_int=int, parse_float=Decimal)`。
  Python `int` 是任意精度，订单号再长也精确；`Decimal` 按十进制原样
  保存字面量，包括末尾的 0（`Decimal("1234.560")` 不丢位）。
- **存储**：
  - `order_id` 存为其十进制规范文本（TEXT + UNIQUE）。sqlite 的 INTEGER
    只有 64 位，19 位以上的订单号会溢出，文本形式对任意长度都精确，
    且 UNIQUE 约束保证 `ingest` 幂等（`INSERT OR IGNORE`）。
  - 金额拆成 `amount_minor`（最小单位的整数值，十进制文本，避免 int64
    溢出）和 `amount_scale`（小数位数）两列。例如 `1234.560` 存为
    minor=1234560, scale=3，是精确的整数表示，不是浮点。
- **导出**：`Decimal(minor).scaleb(-scale)` 后用 `format(..., "f")` 还原
  字面量（不用科学计数法），订单号 `int` 后以不带引号的整数写法输出，
  因此「解析 → 落库 → 读回 → 重新序列化」与原始 JSON 逐字符相等。

## 为什么不直接"存原始文本"

把整行 JSON 原文塞进一个 TEXT 列确实能绕开精度问题，但那是回避而非修复：

- 数据库退化为文件柜：无法对订单号建唯一约束做幂等去重，无法按金额
  比较、汇总、索引，任何校验都要重新解析一遍；
- 原始文本可能携带无关噪声（多余空白、键序变化、`1E2` 这类写法），
  原样回吐会把上游的格式抖动传染给下游对账；
- 缺字段、类型错误的脏数据会被原样吞进库里，问题推迟到读取时才爆发。

本方案存的是**解析并校验过的类型化精确值**（任意精度整数 + 十进制
定点），导出时再按规范形式重新序列化——既保证逐字符往返，又保留了
数据库的约束、校验与查询能力。
