# jobsvc 取消修复说明

## 根因

请求处理把耗时工作派生到后台线程后，取消信号**没有传导路径**：

- 客户端断开 / 请求取消只关闭了连接，工作线程对此一无所知；
- 阻塞 I/O 用一次性的不可中断等待（如 `time.sleep(30)`），期间无法响应任何信号；
- 本地计算是一个无检查点的长循环，跑完才结束。

于是取消后的线程继续跑到自然结束。高峰期这些“幽灵任务”不断堆积，
把 CPU 占满；压测结束后活跃线程数也不下降。

## 修复方案：CancelToken 协作式取消

每个任务持有 `CancelToken`（`jobsvc.py`），取消方调用 `token.cancel()`
（内部是一个 `threading.Event`），执行方在各层**检查点**上观察令牌，
一旦发现取消就抛 `Cancelled`，沿调用栈逐层退出，线程在 `finally` 中
清理（停超时定时器、置 `done`、从活跃集合移除）。

### 取消信号如何穿透每一层

- **I/O 层**：`blocking_io()` 不用一次性 `sleep`，改为 `token.wait()`
  分段可中断等待（每片 ≤ `IO_SLICE` = 10ms）。取消令 Event 置位，
  等待立即返回，最迟一个时间片内观察到信号。
- **本地计算循环**：`compute()` 在每个“计算单元”之间调用
  `token.check()`。单元内的 `hashlib.sha256` 是释放 GIL 的 C 级调用，
  保证 200 个 CPU 密集线程并存时，被取消的线程仍能及时获得调度、
  跑到下一个检查点（实测全部退出约 20ms，远低于 200ms 预算）。
- **入口 / 出口**：线程启动时先 `check()`（启动前已取消则不干活）；
  结果先算到局部变量，通过出口 `check()` 后才写回 `job.result` ——
  取消与正常完成竞争时取消优先，二者互斥。
- **父子传播**：子任务的 token 关联 `parent`，`cancelled()` 沿父链
  递归查询，父任务取消自动级联到所有子任务。
- **超时**：`threading.Timer(timeout, token.cancel)` 到期即触发与
  手动取消完全相同的通路；任务结束时定时器被停掉，不留残留线程。

### 检查点约定（给后续开发者的约定）

1. 任何可能阻塞超过 ~10ms 的调用，必须换成在 token 上可中断的等待；
2. 任何循环，单次迭代耗时 × 迭代间隔不得超过取消延迟预算（200ms），
   否则必须在循环体内放 `token.check()`；
3. 检查点只读令牌、抛 `Cancelled`，不做资源清理；清理由各层
   `finally` 负责；
4. 新增后台任务必须经 `JobService.submit()` 派生，禁止裸起线程。

## 验证

    python3 -m unittest discover -s tests   # 取消/超时/父取消/竞争等 7 例
