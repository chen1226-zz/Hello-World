# jobsvc 取消语义修复

## 根因

请求的处理流程是：HTTP handler 收到请求 → 后台 worker 线程跑 `heavy_compute`
→ 算完再写响应。原实现里取消信号到不了 worker：

1. **I/O 层无检测**：handler 在 `job.done.wait()` 上无限期阻塞，客户端断开
   （连接关闭）或超过截止时间都不会被发现，直到最后写响应才撞上
   `BrokenPipeError`——而那时计算早已跑完。
2. **计算层无检查点**：`heavy_compute` 是一个不可中断的纯 CPU 循环，即使
   有人设置了取消标志，循环内部也从不检查，只能跑完全部工作量。
3. **服务层无归属**：worker 线程游离于任何注册表之外，请求结束后没有
   `cancel/join`，父任务取消也不会传导给子任务。于是客户端断开后线程
   继续空转——压测时这些“幽灵任务”堆积，CPU 被打满，活跃线程数只涨不降。

## 修复：取消信号如何穿透每一层

每个请求创建一个 `CancelToken`（`threading.Event` + 单调时钟截止时间 +
可选父令牌），所有层共享同一个令牌，任一层触发即全局生效：

- **I/O 层（handler）**：等待期间以 10ms 为周期轮询，每轮做两件事——
  `select` + `MSG_PEEK` 探测客户端是否已断开（可读且读到 EOF），以及
  检查令牌是否已取消/超时。任一成立立即 `token.cancel()`。写响应失败
  （`BrokenPipeError`/`ConnectionResetError`）同样触发取消。请求结束时
  在 `finally` 里无条件 `cancel + join`，保证 worker 不活得比请求久。
- **计算层（heavy_compute）**：工作被切成小 chunk（默认每块约 0.1ms），
  **每个 chunk 的循环头部**调用 `token.throw_if_cancelled()`。这是关键
  检查点：取消后 worker 最多再跑一个 chunk 就退出，200ms 预算绰绰有余。
  检查点必须放在循环头部而不是尾部，保证“先检查、后干活”，最后一个
  chunk 也不会漏检。检查点处同时 `time.sleep(0)` 主动让出 GIL：
  纯 Python 计算线程不放行，I/O 线程（accept 循环、handler、客户端）
  会被饿死，取消信号本身也传不进去——这是压测下取消延迟秒级的
  隐藏原因。让行不改变任务总量，只改变调度礼貌性。
- **服务层（JobService）**：登记所有活跃 worker 线程与令牌
  （`active_workers()` 可观测），子令牌可挂到父令牌下（父取消 → 子全部
  取消），`cancel_all()` 用于服务关停时排空一切。worker 退出时在
  `finally` 中注销自己，因此线程数必然回落到基线。此外用“计算槽位”
  信号量（默认 ≈CPU 核数）限制同时烧 CPU 的线程数：高峰期多余的
  worker 在槽位上排队等待，而不是几百个线程一起抢 GIL——这既防止
  CPU 被打满，也把“取消 → 退出”的最坏延迟从 N×调度切片压缩到
  槽位数×调度切片。排队等待同样按 10ms 切片检查令牌，取消的排队
  任务不会等到拿到槽位才发现自己该退出。

超时不是独立机制：令牌带截止时间，`cancelled` 属性把“被显式取消”和
“已过截止时间”统一起来，计算循环的同一个检查点同时覆盖两种情况。

## 检查点约定

1. 任何可能超过几毫秒的循环，**循环头部**必须调用
   `token.throw_if_cancelled()`；纯 CPU 循环还应在检查点 `time.sleep(0)`
   让出 GIL，避免饿死负责传递取消信号的 I/O 线程。
2. 任何阻塞等待（I/O、锁、信号量、队列）必须带超时切片（≤10ms），
   切片边界就是检查点，醒来先查令牌和连接状态。
3. 持有令牌的线程退出前必须在 `finally` 里注销；请求作用域结束时必须
   `cancel + join` 它派生的所有 worker。
4. 新增层（如队列、子任务）通过 `parent=` 链接令牌，不允许另起一套
   取消机制。
