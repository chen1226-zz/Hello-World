# ingest-backpressure

`ingest.py` 是一个接收请求、排队后转发给上游的网关。本目录修复了它在流量
突发时内存单调上涨直到 OOM、P99 从 50ms 恶化到数秒的问题。

## 根因

低流量正常、突发崩溃，典型的无界积压（unbounded backlog）问题，两个因素叠加：

1. **无界排队**：请求到达速率 > 上游消费速率时，请求体在内存里无限堆积，
   RSS 单调上涨直到 OOM。积压量 = (到达速率 − 消费速率) × 时长，没有上限。
2. **没有超载策略**：上游变慢时处理线程被阻塞，新请求仍被全部接受，排队
   等待时间无界增长，P99 随之从 50ms 恶化到秒级；恢复后还要长时间消化积压。

## 修复方案

- **有界队列**：`queue.Queue(maxsize=QUEUE_SIZE)`，在途请求的内存占用有硬上限
  （`maxsize × MAX_BODY`），从根上消除 OOM。
- **超载策略：快速失败（fast-fail / 拒绝）**。队列满时 `POST /ingest` 立即
  返回 `429`，客户端可退避后重试。
  - 为什么选拒绝而不是丢弃最老（drop-oldest）或降级：拒绝的语义最简单、
    可预测——客户端明确知道请求没被接受，可以重试；drop-oldest 会静默丢
    数据而客户端以为成功；降级（如只存不转）实现复杂且仍有堆积风险。
  - 拒绝把压力信号尽早传给调用方，保护上游不被打垮，内存与时延都有界。
- **工作线程池转发**：固定数量的 worker 从队列消费并转发，上游调用带超时；
  转发失败计入 `dropped`，**不重试**（重试会在超载时放大流量，形成重试风暴）。
- **单请求上限**：body 超过 1 MiB 直接 `413`，避免单个大请求撑爆内存。

## 可观测指标

`GET /metrics` 返回 JSON：

| 字段 | 含义 |
| --- | --- |
| `queue_len` | 当前排队长度 |
| `queue_high_water` | 排队长度历史峰值（验证有界） |
| `accepted` / `rejected` | 入队成功数 / 队列满被拒（429）数 |
| `forwarded` / `dropped` | 转发成功数 / 转发失败丢弃数 |
| `p99_seconds` | 最近 4096 个请求的处理时延 P99 |

## 取舍

- 突发期间部分请求被 429 拒绝：用**瞬时可用性**换**系统稳定性和有界恢复时间**。
  突发结束后队列在 `maxsize / 消费速率` 时间内排空，服务立即恢复正常。
- 转发失败不重试：可能丢个别消息，但避免了故障期的流量放大。

## 对外 API（保持不变）

- `POST /ingest` → `202` 已入队 / `429` 超载 / `413` 过大
- `GET /health`、`GET /metrics`

## 运行

```sh
python3 ingest.py                       # 环境变量: PORT UPSTREAM_URL QUEUE_SIZE WORKERS
python3 fake_upstream.py 9000 0.05      # 本机假上游（测试用）
python3 burst_test.py                   # 5 秒 10 倍突发验收: 内存峰值 <= 2x 基线, p99 < 200ms
python3 -m unittest discover -s tests   # 单元测试: 突发/慢消费者/上游变慢/恢复
```
